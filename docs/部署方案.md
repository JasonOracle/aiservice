# aiservice 云端部署方案

> 目标：把「FastAPI 后端 + 双 Next.js 前端 + SQLite + 本地图片」的 MVP，
> 迁移为基于 **TiDB（数据库）+ Cloudflare R2（图片）+ Vercel（前端）+ WebSocket 友好平台（后端）** 的云端部署。
> 预计总工作量：**4~5 个工作日**（含联调实测）。

---

## 一、现状与云端差距（为什么不能直接部署）

| 组件 | 现状 | 云端问题 | 对策 |
|---|---|---|---|
| 主数据库 | SQLite（`backend/data/`） | 平台文件系统易失/不可共享 | **TiDB Serverless**（MySQL 兼容，SQLAlchemy 只改连接串） |
| RAG 检索 | SQLite **FTS5**（`rag.py` 独立连接、独立库文件） | TiDB 无 FTS5 | 重写检索为「关键词记分」或 **TiDB Vector Search**（见 Phase 1） |
| 聊天图片 | 本地磁盘 `uploads/`（Docker 卷） | 平台磁盘重启即丢、多实例不共享 | **Cloudflare R2**（S3 兼容、零出口流量费、可绑自定义域） |
| WebSocket | `/ws/c/{user_id}`、`/ws/agent` 常驻长连接 | **Vercel 不支持持久 WS** → 后端不能放 Vercel | 后端放 Render / Railway / Fly.io |
| Mem0 记忆 | 本地文件 + 内嵌向量 | 同上文件系统问题 | Mem0 向量存储切 **TiDB provider**（官方支持）或暂关 |
| LLM | Dots 网关（公网） | 无问题，云上照连 | 不变 |
| 鉴权 | `/api/upload` 可选鉴权（为 B 端妥协） | 公网暴露风险 | 上线前恢复强制 JWT + 上传限流 |

**关键架构约束（迁移时必须保住）**：
- 会话 ID 约定 `{user_id}::{session_key}`，两端（`conversation_store.py` / `chatStore.ts`）分隔符一致；
- `conversation_store.py` 的函数**永不抛异常**（持久化失败不能打断聊天主链路）；
- 消息时间戳为**毫秒**；`ensure_schema()` 的加列登记机制要改为 MySQL 版；
- 广播协议（`chat_stream` / `agent_message` / `agent_reply` / `handoff_request`）必须继续携带 `images`。

## 二、目标架构

```
                    Cloudflare DNS（域名路由 + HTTPS）
                          │
        ┌─────────────────┼──────────────────┐
        │                 │                  │
   Vercel(toc)        Vercel(tob)      Render/Railway(backend)
   C端 Next.js        B端 Next.js      FastAPI + WS（常驻）
        └────────┬────────┴─────────┬───────┘
                 │ HTTPS API / WS    │
                 ▼                   ▼
           TiDB Serverless ◄──── Mem0(向量存 TiDB)
           （会话/消息/托管/用户/知识库）
                                      │
                     Cloudflare R2 ◄──┘（聊天图片，自定义域直读）
                                      │
                     Dots LLM 网关（公网，不变）
```

- **前端只做静态渲染 + API 调用**，Vercel 免费额度足够；
- **后端选一个支持 WebSocket 的常驻平台**（这是唯一没有"你已有账号"覆盖的部分，三选一）；
- **TiDB Serverless** 免费额度：行存储 + 向量检索都覆盖本项目量级。

## 三、分阶段计划

### Phase 0｜前置盘点与账号准备（0.5 天）
- [ ] TiDB Serverless 建集群，拿连接串（含 SSL 参数），白名单 0.0.0.0/0 或平台出口 IP
- [ ] Cloudflare R2 建桶 + API Token（Access Key / Secret），绑定自定义域如 `cdn.你的域名`
- [ ] 选定后端平台（Render / Railway / Fly 三选一）并注册
- [ ] 盘点代码中所有 `sqlite3` 直连与 `uploads` 引用点（已摸底：`database.py`、`conversation_store.py`、`models.py`、`rag.py`、`chat_images.py`、`memory.py`、`seed*.py`）

### Phase 1｜数据层迁移 TiDB（1~2 天，核心工作量）
1. **主库**（`database.py`）：
   - 连接串改 `mysql+pymysql://...ssl_ca=...`，连接池加 `pool_pre_ping=True`（Serverless 空闲断连）
   - `ensure_schema()` 重写为 MySQL 方言（`CREATE TABLE IF NOT EXISTS` + 补列逻辑改为 `information_schema` 查询后 `ALTER TABLE ADD COLUMN`）
   - 时间戳字段统一 `BIGINT`（毫秒），布尔字段 `TINYINT(1)`
2. **RAG**（`rag.py`，FTS5 → 二选一）：
   - **方案 A（推荐先做）**：关键词记分检索 —— 把现在的 FTS5 `MATCH` 查询改写为 `LIKE '%kw%'` + Python 侧记分（虚词黑名单、`TITLE_WEIGHT=3.0`、`MIN_RELEVANCE=0.30` 逻辑全部保留），16 篇文档量级下性能完全够
   - **方案 B（增强，可选）**：TiDB Vector Search（`VECTOR` 列 + `VEC_COSINE_DISTANCE`），需要 embedding 模型 —— 先验证 Dots 是否提供 `/v1/embeddings`，不提供则换 bge/m3e 免费源或暂用方案 A
3. **Mem0**（`memory.py`）：vector store 配置为 `tidb` provider（官方支持），LLM 用 Dots；若排查成本高，先以 `MEMORY_ENABLED=false` 开关降级上线
4. **种子脚本**：`seed.py` / `seed_kb.py` / `seed_demo.py` 改走 TiDB（幂等逻辑保留）
5. **验收**：本地裸跑 backend 连云上 TiDB，三端全链路回归（登录、发消息、图片、托管、handoff）

### Phase 2｜图片迁移 Cloudflare R2（0.5~1 天）
- `chat_images.py`：`save_chat_image()` 改为 S3 兼容上传（`boto3`，endpoint 指向 R2），返回**完整公网 URL**（自定义域）
- `routers/upload.py` 返回值兼容：新图返回绝对 URL，老数据里的相对路径 `/uploads/...` 前端 `mediaUrl()` 保留兜底拼接
- `ai_engine.py` 的 base64 内联逻辑改为：直接 fetch R2 公网 URL 转 base64（或 R2 图本就是公网 URL，按模型要求处理）
- 验收：C/B 端发图 → 大图预览 → AI 识图 → 跨设备查看

### Phase 3｜后端上云（0.5~1 天）
- 以 **Render Web Service** 为默认方案（备选 Railway）：
  - 连 GitHub 仓库，Root Directory = `backend`，启动命令 `uvicorn main:app --host 0.0.0.0 --port $PORT`
  - 健康检查路径 `/api/health`
  - 环境变量：`DATABASE_URL`、`XIAO_HONG_SHU_API_KEY`、R2 三件套、`MEMORY_ENABLED`、`CORS_ORIGINS`
- `main.py` CORS 收紧为前端两个正式域名
- **WS 实测**：`/ws/c/{user_id}` 与 `/ws/agent` 在云域名下握手、`handoff_request` 广播、坐席实时回复（WS 过 CDN 时注意平台是否直连，Render/Railway 原生支持，不经 Cloudflare 代理更稳）

### Phase 4｜前端部署 Vercel（0.5 天）
- toc、tob 各建一个 Project，同一仓库选目录 `toc/` / `tob/`
- 环境变量：`NEXT_PUBLIC_API_BASE=https://api.你的域名`（及各自登录口令）
- 检查 `toc/lib/api.ts` 与 `tob/lib/api.ts`：所有 fetch 走环境变量；WS 地址同步替换
- `mediaUrl()`：R2 绝对 URL 直接返回，`/uploads/` 相对路径兜底拼后端域名

### Phase 5｜域名、安全加固（0.5 天）
- Cloudflare DNS：`www` → Vercel(toc)、`admin`（或 `b`）→ Vercel(tob)、`api` → 后端平台、`cdn` → R2
- 安全项（上线必做）：
  - `/api/upload` 恢复**强制 JWT**（B 端坐席补 token，`tob/lib/api.ts` 已带鉴权头）
  - 上传加**限流 + 大小/类型校验**（已有 MAX_IMAGE_BYTES，补频率限制）
  - 所有管理接口鉴权复核（`/api/conversations`、`/api/ai-custody` 由可选改必选或加口令）
  - `.env` 全部走平台密钥管理，确认 git 无泄漏（已验证）
- 演示数据决策：**建议线上清库重灌真实知识库（seed_kb），不带 seed_demo 演示会话**

### Phase 6｜端到端实测与文档（0.5 天）
- 全链路：注册登录 → 商品咨询 → 发图 → AI 识图 → 争议类转人工 → B 端收到 `handoff_request` → 坐席回复 → 托管开关生效 → **换设备登录历史可见**
- 压测口径：并发 10 路聊天消息 + WS 广播无丢失
- 更新 `docs/progress.md`、`docs/technical_implementation.md`（数据模型/接口不变，部署架构重写）

## 四、待确认的三个决策点

| # | 决策 | 推荐 | 理由 |
|---|---|---|---|
| 1 | 后端平台：**Render / Railway / Fly.io** | Render | 免费实例可起步、原生 WS、GitHub 自动部署；Railway 更快但按用量计费 |
| 2 | RAG 检索：**关键词记分 / TiDB 向量** | 先记分、后向量 | 记分方案一天可落地且保住"检索不到就转人工"的高压线；向量检索作为二期增强 |
| 3 | Mem0：**接 TiDB 向量 / 暂时关闭** | 先关闭、后接入 | 记忆是加分项不是主链路，先用开关降级，避免部署被它卡住 |

## 五、风险清单
- **WS 兼容**：若后端域名套了 Cloudflare 代理（橙色云），长连接可能被断——后端子域建议灰云直连或使用平台原生域名
- **TiDB 连接数**：Serverless 免费版连接数有限，backend 需连接池复用（SQLAlchemy 默认即可），禁止单请求多连接
- **FTS5 → 记分检索的召回差异**：中文分词行为不同，上线前用 16 篇知识库的典型问法做一轮回归，重点盯 `MIN_RELEVANCE` 边界
- **老图片路径**：本地演示数据里的 `/uploads/...` 相对路径在云端 404，属预期，可接受或重灌
- **Vercel 冷启动**：Next.js 首次访问慢几秒，演示前先预热
